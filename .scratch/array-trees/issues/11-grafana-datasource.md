## Question

`[[06-benchmark-storage]]` решил: своё хранилище, не Prometheus/Pushgateway. Не выбрана конкретная технология и схема подключения к Grafana:

- что именно за хранилище (SQLite-файл, Postgres, файлы Parquet/CSV + плагин, что-то ещё) — с учётом, что записи пишутся батчем по итогам прогона, а не потоково;
- какой Grafana data source читает это хранилище (встроенный SQL data source, JSON API плагин, CSV/файловый плагин);
- форма дашборда: сравнение 4 реализаций × операция × форма дерева × `n`/`d`/`c` — сколько панелей, какая группировка (по операции? по реализации? overlay всех четырёх на одном графике?), нужно ли отдельно визуализировать компромисс время/итерации из `[[10-benchmark-protocol]]`.

## Answer

### Хранилище и подключение

**Postgres.** Батчевая запись (раз за прогон, не потоково) не оправдывает свой сервис по нагрузке, но у Grafana для Postgres — **нативный** data source без сторонних плагинов, в отличие от SQLite (community-плагин). Учитывая, что дашборд — не разовая вещь, а постоянный инструмент сравнения, нативная поддержка перевесила простоту SQLite.

Grafana подключается напрямую этим нативным Postgres data source к таблице ниже — отдельного API/сервиса перед Postgres не нужно.

### Схема

Одна плоская таблица, **строка на один "горячий" сэмпл** (не массив на прогон — иначе каждый Grafana-запрос требовал бы `UNNEST`):

```sql
CREATE TABLE benchmark_samples (
  id             BIGSERIAL PRIMARY KEY,
  run_at         TIMESTAMPTZ NOT NULL,
  implementation TEXT NOT NULL,   -- cxx_parallel_stl | cxx_simd | go_stdlib | go_simd
  shape          TEXT NOT NULL,
  case_id        TEXT NOT NULL,
  op             TEXT NOT NULL,
  nodes_count    BIGINT NOT NULL,
  depth          BIGINT,                 -- NULL, если не применимо
  sample_index   INT NOT NULL,           -- 0..N-1 внутри прогона, после warm-up
  timing_ns      BIGINT NOT NULL,        -- длительность одного "горячего" замера
  iterations     INT,                    -- NULL, если операции не подходит
  peak_rss_delta_bytes BIGINT            -- NULL в batch-режиме (`[[10-benchmark-protocol]]`)
);
```

`timing_ns` — обычный `BIGINT`, не `INTERVAL` (у `INTERVAL` точность до микросекунд и он семантически про календарные интервалы, не про счётчик наносекунд производительности).

### Дашборд

- **Два скейлинг-графика** (линейные, X в лог-масштабе): `x = nodes_count` на форме `wide-shallow`, `x = depth` на форме `degenerate-chain` (обе серии — `[[10-benchmark-protocol]]`). Линия на реализацию; для propagation-операций — отдельная линия на каждую из трёх стратегий.
- **Парная панель iterations** рядом с каждым скейлинг-графиком propagation-операций, тот же `x`, **отдельная панель**, не dual-axis (dual-axis с двумя разными масштабами провоцирует ложные визуальные корреляции) — покрывает обязательное правило парности из `[[10-benchmark-protocol]]`.
- **Та же пара форм (скейлинг-график + столбец в общей таблице) повторяется для памяти** (`peak_rss_delta_bytes`), тем же способом, что и для времени.
- **Одна общая фильтруемая таблица-панель** для всех фиксированных форм × операций (не по панели на каждую комбинацию — комбинаторно взрывается): `implementation`, `shape`, `op`, агрегат `timing_ns` (медиана/перцентиль считается в самом запросе Grafana, не в момент записи), `iterations`, `peak_rss_delta_bytes`.
- **Отдельной метрики ЦП не вводится.** Сравнение «по нагрузке на процессор» между последовательными и параллельными/SIMD-реализациями покрывается уже существующими панелями по `timing_ns` — не заводим `cpu_time_ns` (`ru_utime+ru_stime`) и производный коэффициент использования ядер.
