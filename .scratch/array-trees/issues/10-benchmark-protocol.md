## Question

Пользователь хочет сравнивать 4 реализации не только на корректность, но и на скорость (`parallel STL`/SIMD против последовательной/stdlib логики). `08-array-trees.md` §5.3 явно предупреждает про компромисс: однопроходная последовательная версия — `1 × O(n)`, итеративная/параллельная — `d × O(n)` (или `O(log d)` с pointer doubling, §5.4). Замер только wall-clock без числа проходов сделает параллельные варианты выглядящими произвольно хуже или лучше в зависимости от формы дерева.

Не зафиксировано:

- какие значения `n` (число узлов), `d` (глубина) и `c` (максимальное число детей у родителя) варьировать в бенчмарках, и варьировать ли их независимо друг от друга, или только в рамках фиксированных форм из `[[03-test-corpus]]`;
- число повторов на измерение и правила прогрева (warm-up), чтобы шум JIT/кэша/CPU throttling не искажал сравнение между C++ (AOT) и Go (компилируется, но со своим рантаймом/GC);
- обязательный ли параллельный вывод в отчёте — время **и** число проходов/итераций рядом, для каждой стратегии propagation отдельно — чтобы не терять компромисс §5.3 при построении графиков.

## Answer

### Формы и параметры

Бенчмарки прогоняются только на фиксированных формах `[[03-test-corpus]]` — без отдельной параметризованной сетки `n`/`d`/`c`, один канонический генератор данных для корректности и скорости. Единственное отличие бенчмарка от корректностного прогона — `--repeat` больше 1.

Плюс две серии масштабирования (расширение корпуса, см. правку `[[03-test-corpus]]` ниже), с полноценными golden по общей логике:

- **По `n`**: форма `wide-shallow`, `d≈10` фиксирована, `n ∈ {10³, 10⁴, 10⁵, 10⁶}` — изолирует последовательное `O(n)` от глубины.
- **По `d`**: форма `degenerate-chain`, `n = d`, `d ∈ {10³, 10⁴, 10⁵, 10⁶}` — изолирует наивный подъём/итеративный propagation (`O(d)`) от binary lifting/pointer doubling (`O(log d)`).

### Повторы и прогрев

Повтор — **внутри процесса**, не на уровне процесса (правка `[[09-cli-schema-details]]`): CLI парсит дерево один раз, затем крутит операцию `--warmup W` (default 3) раз без учёта, затем `--repeat N` (default 20) раз с учётом. `timing_ns` в выводе — массив ровно из `N` «горячих» сэмплов; фильтрация холодных — забота CLI, не внешнего драйвера/хранилища.

### Батч-режим (`--manifest`)

Новый режим ввода CLI, отдельно от одиночного `--tree`/`--case`: `--manifest <path>` — файл со списком сценариев `[{"tree": "...", "case": "...", "repeat": N}, ...]`. CLI парсит каждый уникальный corpus-файл один раз на весь манифест (не по разу на сценарий), гоняет все сценарии, отдаёт массив результатов в том же порядке. Одиночный режим остаётся основным для проверки корректности (проще параллелить между вызовами извне); манифест — только для бенчмарков, где повторный парсинг больших corpus-файлов (миллионы листьев) на каждый сценарий — лишние накладные расходы.

### Память

Меряется **только в одиночном режиме**, не в `--manifest` — общий процесс контаминирует RSS между сценариями батча, изоляция и батчинг тянут в разные стороны. Метрика — дельта peak RSS (`getrusage`/`ru_maxrss` на Linux) между снимком сразу после парсинга дерева (до операции) и снимком сразу после операции. OS-уровня метрика выбрана намеренно — она сравнима между C++ (RAII/`new`/`delete`) и Go (GC), в отличие от языкоспецифичных счётчиков аллокатора. Новое поле конверта — `peak_rss_delta_bytes`.

### Обязательная парность time+iterations

Протокольное правило: хранилище (`[[06-benchmark-storage]]`) обязано хранить `iterations` рядом с каждым `timing_ns`-сэмплом propagation-операций, не терять пару при агрегации; любой дашборд (`[[11-grafana-datasource]]`), показывающий время propagation-операции, обязан показывать и `iterations` — иначе теряется компромисс §5.3 (`1×O(n)` последовательно vs `d×O(n)`/`O(log d)` параллельно), ради которого всё сравнение затевается.
