## Question

`[[05-cli-contract]]` установил: единый CLI-контракт для всех 4 реализаций, JSON вход/выход, результат + метрики. Не зафиксировано:

- точный набор подкоманд/флагов (одна операция за вызов? список операций? как передаётся стратегия propagation, когда операция имеет несколько вариантов — §5.1/§5.3/§5.4);
- конверт вывода: структура `{result, timing, iterations, ...}` — единая для всех категорий операций из `[[02-operation-set]]` или своя на категорию;
- как кодируется провал валидации инвариантов §13 (специальный код возврата? поле в JSON-конверте?);
- конвенция кодов возврата и формата ошибок (некорректный JSON на входе, неизвестная операция, испорченное дерево, не прошедшее §13, когда операция этого не ожидала).

## Answer

### Вызов — одиночный режим

```
runner --tree corpus/<shape>.json --case cases/<shape>/<case_id>.json [--warmup W] [--repeat N]
```

- `--tree` — путь к corpus file (`[[08-json-schema]]`).
- `--case` — путь к файлу одного кейса, `{"op": "...", "args": {...}}`; `args` отсутствует, если операция параметров не требует (например, `{"op": "depth"}`).
- `--warmup W` (default 3) / `--repeat N` (default 20) — **исправлено при работе над `[[10-benchmark-protocol]]`**: повтор — внутри процесса (дерево парсится один раз, до всех прогонов), не на уровне процесса. CLI сам прогревает и отбрасывает холодные сэмплы.
- Для корректностных прогонов (не бенчмарк) достаточно `--repeat 1` — тогда прогрев не нужен, `--warmup` можно не передавать или задать 0.

### Вызов — батч-режим (добавлено `[[10-benchmark-protocol]]`)

```
runner --manifest benchmarks/wide-shallow-scaling.json
```

Манифест — `[{"tree": "...", "case": "...", "repeat": N}, ...]`. CLI парсит каждый уникальный `tree`-файл один раз на весь манифест, гоняет все сценарии по очереди, отдаёт JSON-массив результатов в том же порядке, что сценарии в манифесте. `--tree`/`--case`/`--manifest` — взаимоисключающие режимы, не смешиваются в одном вызове. Замер памяти (см. ниже) в этом режиме не производится.

### Успешный вывод (`exit 0`, stdout)

Одиночный режим:
```json
{"result": <value>, "timing_ns": [184032, 179001, ...], "iterations": 3, "peak_rss_delta_bytes": 40960}
```
Батч-режим — массив объектов той же формы, без `peak_rss_delta_bytes` (по одному на сценарий манифеста, в его порядке).

- `result` — та же форма, что в golden-файле для этого `op` (`[[08-json-schema]]`).
- `timing_ns` — **массив** из `N` «горячих» сэмплов (наносекунды), холодные (`--warmup`) в вывод не попадают. **Исправлено `[[10-benchmark-protocol]]`** — было одно число.
- `iterations` — число проходов/итераций до сходимости; `null` для операций, которым понятие не подходит (LCA, мутации, DFS/BFS-переупорядочивание, производные вектора). Заполняется для всех трёх propagation-стратегий и для `validate_invariants` (сходимость `<=n`, §13). Протокольное правило (`[[10-benchmark-protocol]]`): хранилище и дашборды обязаны показывать `iterations` рядом с `timing_ns`, никогда время propagation-операции отдельно.
- `peak_rss_delta_bytes` — **добавлено `[[10-benchmark-protocol]]`**, только в одиночном режиме: дельта peak RSS (`getrusage`/`ru_maxrss`) между снимком сразу после парсинга дерева и снимком сразу после операции. Не измеряется в батч-режиме (общий процесс контаминирует RSS между сценариями).
- Провал §13-валидации (`result.valid == false`) — это **не ошибка**, а обычный успешный ответ операции `validate_invariants`, `exit 0`.

### Ошибки (`exit 1`, stderr)

```json
{"error": "unknown_op", "message": "человекочитаемое описание"}
```

`error` — snake_case-код из фиксированного набора: `invalid_tree_json`, `invalid_case_json`, `unknown_op`, `args_mismatch`, `file_not_found`. Один общий exit code (`1`) для всех ошибок контракта — различать коды по типам избыточно для тестового раннера, тип ошибки уже есть в `error`. stdout при ошибке пуст — драйвер по exit code сразу понимает, что stdout не нужно парсить как результат.
