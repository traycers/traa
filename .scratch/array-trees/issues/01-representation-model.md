## Question

Дерево у Hsu (`docs/learning/array-trees/`) — это структурные вектора `parent`+`sibling` (плюс производные `depth`/`rank`/`size`/`nsibling`/`lastchild`/`isleaf`, которые не хранятся, а вычисляются, §3.5–§4) и отдельно, в некоторых системах — полезная нагрузка узла: типизированное значение с закрытым набором физических представлений.

Какое именно представление дерева должны реализовать все 4 реализации traa — только структуру, или ещё и типизированный payload? Хранить производные вектора или вычислять по вызову?

## Answer

Дерево traa — **три параллельных массива** (SoA): `parent`, `sibling`, `data`.

- `parent[i]`, `sibling[i]` — id-ссылки и тот же инвариант порядка (`parent[i] <= i`, `sibling[i] <= i`), что в теории Hsu (§3.6, §13), uint32.
- Производные вектора (`depth`, `rank`, `size`, `nsibling`, `lastchild`, `isleaf`, `pos`) **не хранятся** — это чистые функции от `parent`/`sibling`, вычисляются по вызову (пропагацией §5–§6 или способом Б §8.2 для `pos`/`size`). traa берёт пару `parent`+`sibling` как теоретическую модель Hsu, в собственной, простой раскладке — 3 параллельных массива (SoA), без структуры-узла (AoS).

Из мутаций (§11) в объём входит полный набор §4–§11 (см. [[02-operation-set]]), а не только минимальный набор, нужный какому-то одному конкретному формату, — сравнение реализаций требует всех операций.

### Payload — исправлено

Первая версия этого ответа ошибочно скопировала закрытый доменный список типов (`void`/`uint8`/`uint32`/`float64`/`timestamp`/`bytes`, ориентированный на конкретный медиа-формат) — а traa нужно **шаблонное дерево**, не привязанное к чужому домену.

Исправленное решение: `data[i]` — массив **одного generic-параметра `T`**, который выбирает вызывающий код при инстанцировании дерева, а не сама библиотека дерева:

```cpp
template<typename T>
struct Tree { std::vector<uint32_t> parent, sibling; std::vector<T> data; };
```
```go
type Tree[T any] struct { Parent, Sibling []uint32; Data []T }
```

Все узлы одного конкретного дерева несут значения одного и того же типа `T` (однородный payload). Гетерогенный payload (разные узлы — разные типы через tagged union/`any`) обсуждался и сознательно отклонён в пользу простого однородного generic — см. обсуждение в чате карты.

Открыто (см. `[[08-json-schema]]`): каким(и) конкретными `T` инстанцируется дерево в языконейтральном тестовом корпусе, раз сам корпус — один и тот же JSON для всех 4 реализаций.

Контекст: `[[02-operation-set]]`, `[[04-corpus-golden-format]]`, `[[08-json-schema]]`.
