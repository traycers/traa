# Реальное состояние тулчейна для 4 реализаций array-tree

Проверка по первоисточникам вопроса из `issues/07-toolchain-reality.md`. Каждый пункт разделён на **[ЛОКАЛЬНО]** — проверено в этом окружении командами/чтением файлов репозитория — и **[ИСТОЧНИК]** — официальная документация/трекеры выше по течению.

## 0. Важная методологическая оговорка: это окружение — не `cxx/Dockerfile.dev`

**[ЛОКАЛЬНО]** Перед разбором по пунктам: текущая live-сессия **не является** контейнером, собранным из `cxx/Dockerfile.dev`, хотя ОС совпадает (`Ubuntu 26.04 LTS "resolute"`, `/etc/os-release`). Расхождения:

- `clang` бинарь отсутствует (`clang: command not found`), хотя `Dockerfile.dev` явно ставит пакет `clang` (строка 12). При этом `dpkg -l` показывает только `libclang-cpp21`/`libclang1-21` (библиотеки, не сам компилятор), а `apt-cache policy clang` показывает кандидат `1:21.1.6-71`, но **не установлен**.
- `/.dockerenv` отсутствует, `cat /proc/1/cgroup` даёт `0::/init.scope` — типичный признак systemd-хоста, а не контейнера от `docker build`.
- Установленный компилятор — `gcc (Ubuntu 15.2.0-16ubuntu1) 15.2.0`, которого нет в списке пакетов `Dockerfile.dev` вовсе (там только `build-essential`, который тянет `gcc`/`g++` дистрибутивной версии — 15.2.0 на Ubuntu 26.04 это ожидаемо для `build-essential`, так что этот пакет хотя бы согласован).
- `.clangd` (файл `cxx/.clangd`, строки 25–26) жёстко прописывает пути `/usr/include/c++/16` — то есть **GCC 16**, которого в системе нет (есть только `/usr/include/c++/15`). Также `.clangd` ссылается на `-isystem/usr/include/drogon` и `-isystem/usr/include/immer` — эти пакеты не упоминаются больше нигде в репозитории и не имеют отношения к array-tree задаче; похоже на нетронутый boilerplate от шаблонного репозитория, а не актуальную конфигурацию проекта.

**Вывод методологический**: результаты `go version`, `gcc --version`, состояние `dpkg` в этой сессии показывают, что *доступно прямо сейчас в среде агента*, но не обязательно то, что будет в реальном `cxx/Dockerfile.dev`-контейнере или на CI. Однако `apt-cache policy` подтверждает, что нужные пакеты (`clang`, `libboost-all-dev`, `libtbb-dev`) как минимум **доступны в репозиториях Ubuntu 26.04** ("resolute"/universe) — то есть их можно доустановить в `Dockerfile.dev`, вопрос только в том, что сейчас их там нет.

## 2. Go `simd` — публичный пакет

**[ИСТОЧНИК]** Существует два разных пакета под общим "простонародным" именем "Go simd", оба гейтятся `GOEXPERIMENT=simd`, оба публичные (не `internal/`), по дизайн-предложению **golang/go#73787** ("simd/archsimd: architecture-specific SIMD intrinsics under a GOEXPERIMENT", статус — **Proposal-Accepted**, milestone Backlog):

- **`simd/archsimd`** — низкоуровневый, архитектурно-специфичный API. Появился в **Go 1.26** (амд64: 128/256/512-битные векторы, AVX-512 на части процессоров) под `GOEXPERIMENT=simd`. В **Go 1.27** API amd64 пересмотрен и добавлена поддержка ARM64 (Neon, 128 бит) и WebAssembly (128 бит). Типы — непрозрачные структуры вида `Uint32x4`, `Uint32x8`, `Float64x4`, маски — `Mask32x4` и т.п. Операции: `Add/Sub/Mul/Min/Max`, побитовые `And/Or/Xor/AndNot`, сдвиги/ротации, сравнения `Equal/GreaterThan`, `Blend/Compress/Expand/Permute`, конверсии типов, `Load`/`Store` по типизированным указателям на массивы. Это ровно тот набор примитивов, что нужен для propagation по `uint32`-векторам `parent`/`sibling` и битовым маскам.
- **`simd`** (портируемый, верхнеуровневый пакет с "неопределённым" размером вектора, вроде `Int8s`/`Float32s`) — экспериментально появляется в **Go 1.27** (проектное предложение **golang/go#78902**), тоже под `GOEXPERIMENT=simd`, доступен на всех архитектурах (падает на software-эмуляцию там, где нет аппаратной поддержки). API обоих пакетов **не стабилизирован**.

И `simd`, и `simd/archsimd` требуют явного `GOEXPERIMENT=simd` при сборке toolchain/бинаря — обычный `go build` без этой переменной их не подключит.

Источники: go.dev/doc/go1.26, go.dev/doc/go1.27, github.com/golang/go/issues/73787, github.com/golang/go/issues/78902.

**Вывод для проекта**: "Go simd" из формулировки задачи реалистичен, но требует **как минимум Go 1.26** (для `simd/archsimd`) или **Go 1.27** (если нужен портируемый верхнеуровневый `simd`), и в обоих случаях — обязательный `GOEXPERIMENT=simd`. Локально стоит 1.26.0 — `simd/archsimd` доступен уже сейчас, `simd` (портируемый) — нет, нужен апгрейд до 1.27.

## 3. Boost.SIMD и живые преемники

**[ИСТОЧНИК]** Boost.SIMD **никогда не был принят** в основной дистрибутив Boost. Это был выделенный из проекта NT2 (numerical template toolbox) кандидат на review; попытки внесения на review шли ~2014 год (см. рассылки lists.boost.org, "NT² 3.0 and Boost.SIMD — Stable release", февраль 2014), но формального принятия не случилось. Проект впоследствии стал неактивным, репозиторий был переименован/переброшен в `agenium-scale/boost.simd` — issue `#545 "The state of boost.simd"` в этом репозитории фиксирует застой; проект был ребрендирован в **bSIMD** под более рестриктивной (коммерческой) лицензией.

Живые преемники:

| Библиотека | Статус | Лицензия | Header-only | Стандарт | Установка |
|---|---|---|---|---|---|
| **xsimd** (github.com/xtensor-stack/xsimd) | Активна, используется Firefox/Apache Arrow/Pandas | BSD-3-Clause | header-only (`include/xsimd`) | C++17+ | conda-forge, Spack; нет официального vcpkg/conan в самом README, но `vcpkg install xsimd` де-факто существует в реестре vcpkg (не подтверждено первоисточником README проекта) |
| **Google Highway** (github.com/google/highway) | Активна, v1.0+, упор на обратную совместимость | Apache-2.0 / BSD-3 (двойная) | **не** header-only — требует сборки/линковки (CMake/Bazel/Meson) | C++17 (только языковые фичи) | vcpkg (`vcpkg install highway`), Conan, Homebrew, conda-forge, Spack |
| **`std::experimental::simd`** (Parallelism TS2, `<experimental/simd>`) | Живёт в libstdc++ **с GCC 11** | часть libstdc++ (GPL-3 + GCC runtime exception) | header-only, часть системного toolchain, **не требует отдельной установки** | доступен под `-std=c++17/20/23`, не только `-std=c++26` | ничего доустанавливать не нужно — уже есть в системном GCC |
| **`std::simd` (C++26, P1928)** | P1928 внесён в стандарт C++26; в GCC — работа в процессе (частичная реализация с GCC 14+, `simd.loadstore`/`simd.permute.dynamic`/часть `simd.math` ещё не реализованы по состоянию на последние патчи) | как выше | header-only, часть будущего libstdc++ | требует `-std=c++26`, для которого текущая реализация в GCC **неполная** | не нужно доустанавливать, но нельзя полагаться на полноту |

**[ЛОКАЛЬНО]** Подтверждено чтением файловой системы: `/usr/include/c++/15/experimental/simd` **существует** в этом окружении (GCC 15.2.0) — то есть `std::experimental::simd` доступен прямо сейчас без единой доп. установки. `libboost-all-dev` в системе **не установлен**, но кандидат `1.90.0.1ubuntu3` доступен в `resolute/universe` — то есть сам исторический "Boost.SIMD" всё равно не появится через `apt install libboost-all-dev`, потому что его никогда не было в самом Boost (см. выше — не вопрос версии пакета, а факт истории проекта).

Источники: lists.boost.org (тред "NT² 3.0 and Boost.SIMD"), github.com/agenium-scale/boost.simd issue #545, serge-sans-paille.github.io ("Bye bye boost.simd, welcome xsimd"), github.com/xtensor-stack/xsimd (README), github.com/google/highway (README), open-std.org P1928r15 (WG21), gcc.gnu.org/onlinedocs/libstdc++/manual/status.html, gcc-mirror/gcc `libstdc++-v3/include/experimental/simd`.

## 4. Parallel STL на этом тулчейне

**[ИСТОЧНИК]** Официальная документация GCC/libstdc++ (`gcc.gnu.org/onlinedocs/libstdc++/manual/status.html`) прямым текстом: *"The Parallel Algorithms have an external dependency on Intel TBB 2018 or later. If the `<execution>` header is included then `-ltbb` must be used to link to TBB."* Это требование действует с **GCC 9.1** (первая версия со стандартизированными parallel algorithms из C++17) и **не отменено** ни в одной последующей версии — официальный источник не упоминает встроенной альтернативы или снятия этой зависимости в GCC 13 или позже; предположение из исходного вопроса ("GCC 13+ вроде получил встроенную параллелизацию без TBB") **не подтверждается** первоисточником и должно считаться неверным для libstdc++.

Отдельно: страница `gcc.gnu.org/onlinedocs/libstdc++/manual/parallel_mode.html` описывает **другую**, устаревшую фичу — "libstdc++ parallel mode" (GNU-специфичное расширение под C++03, `_GLIBCXX_PARALLEL`), не относящуюся к стандартным `std::execution::par`/`par_unseq`; сама страница признаёт, что не была обновлена под современные стандарты, и отсылает к обычным C++17 execution policies вместо себя. Не перепутать эти две вещи.

**[ЛОКАЛЬНО]** В системе установлены **только рантайм-библиотеки** TBB — `libtbb12`, `libtbbbind-2-5`, `libtbbmalloc2` (все версии `2022.3.0-2`), но **не** `libtbb-dev` (dev-пакет с заголовками и `.so`-симлинком для линковки в момент сборки) — он отсутствует, хотя кандидат `2022.3.0-2` доступен в `resolute/universe`. То есть на сборку `<execution>`-кода с `par_unseq` этого недостаточно: без `libtbb-dev` компиляция/линковка кода, включающего `<execution>` и вызывающего параллельные алгоритмы, не пройдёт (`-ltbb` не найдёт заголовков `tbb/tbb.h` и, возможно, дев-симлинка библиотеки).

По поводу связки "clang + системный libstdc++": `<execution>` — часть libstdc++ (не libc++), значит если clang собирается с `-stdlib=libstdc++` (как явно прописано в `.clangd`: `-stdlib=libstdc++`, `--gcc-toolchain=/usr`), то `<execution>` физически доступен (тот же путь `/usr/include/c++/15`, где, к слову, обнаружен `experimental/simd`, но не проверялся отдельно путь `<execution>` — по логике libstdc++ он там тоже есть, т.к. это единый дистрибутив заголовков GCC 9.1+). Требование TBB для реальной параллельности при этом сохраняется независимо от компилятора (clang или gcc) — TBB-зависимость идёт от **реализации библиотеки** (libstdc++), а не от компилятора.

Дополнительно зафиксировано (не решается этим тикетом): в `Dockerfile.dev` (строка 1) — `FROM ubuntu:26.04`. **[ЛОКАЛЬНО]** подтверждено — `ubuntu:26.04` "Resolute Raccoon" на текущую дату (сентябрь 2026) реален и используется этим самым окружением (`/etc/os-release`), то есть базовый образ существует и это не проблема на момент этого исследования (риск, отмеченный в исходном вопросе, снят по времени, а не по факту его когда-то отсутствия).

Источники: gcc.gnu.org/onlinedocs/libstdc++/manual/status.html, gcc.gnu.org/onlinedocs/libstdc++/manual/parallel_mode.html, dpkg/apt-cache policy этого окружения.

## 5. Реальное состояние конфигурации репозитория

**[ЛОКАЛЬНО]**, чтение файлов:

- **`cxx/Dockerfile.dev`** — устанавливает: `build-essential`, `cmake`, `ninja-build`, `ca-certificates`, `libgtest-dev`, `libgmock-dev`, `clang`, `clangd`, `clang-tidy`, `clang-format`, `git`, `sudo`. **Нет** ни Boost, ни TBB (ни `libtbb-dev`, ни рантайма), ни xsimd/Highway. Базовый образ — `ubuntu:26.04`.
- **`cxx/.devcontainer/devcontainer.json`** — просто указывает на `Dockerfile.dev` как контекст сборки, добавляет VS Code расширения (clangd, cmake-tools, lldb и т.п.), `runArgs` с `SYS_PTRACE`/`seccomp=unconfined` (для отладчика/санитайзеров). Никаких доп. пакетных зависимостей не описывает — вся ответственность на Dockerfile.
- **`cxx/CMakeLists.txt`** — `CMAKE_CXX_STANDARD 23` (не 26 — значит `std::simd` из C++26/P1928 в принципе недоступен на этом стандарте языка, даже если бы GCC его полностью реализовал; доступен только `std::experimental::simd`, который стандарту языка не привязан жёстко к C++26). `PROJECT_DEPS` — пустой список (закомментированный `# PKG <package_name>`), т.е. **сейчас никакие внешние find_package зависимости не подключены вообще**. Использует свой `find_pkgs`/`find_deps` DSL (см. ниже) и обязательный `GTest` при `USE_TEST=ON` (по умолчанию включено).
- **`cxx/cmake/files/find_deps.cmake`** и **`find_pkgs.cmake`** — вспомогательные функции для декларативного описания `find_package(PKG ... COMPONENTS ...)` через списки вида `PKG Boost COMPONENTS headers`; сами по себе ничего не подключают, это инфраструктура, ожидающая заполнения `PROJECT_DEPS`/аналогичных списков.
- **`cxx/CMakePresets.json`** — подключает `configure/{base,clang,gcc,debug,relwithdebinfo}.json` и san-варианты. `clang.json`/`gcc.json` задают только `CMAKE_CXX_FLAGS: "-Wall -Wextra -Werror -Wno-attributes"` — **не указывают явно компилятор** (`CMAKE_CXX_COMPILER`) в увиденных пресетах верхнего уровня; выбор компилятора, судя по всему, идёт через переменные окружения `CC`/`CXX` или отдельные (не прочитанные целиком в этой сессии) toolchain-файлы `$env{CMAKE_TOOLCHAIN_FILE_DEBUG}`/`$env{CMAKE_TOOLCHAIN_FILE_RELWITHDEBINFO}` (ссылки на них есть в `configure/debug.json`/`relwithdebinfo.json`, но сами toolchain-файлы не были прочитаны в рамках этого исследования — если понадобится проверить, какой конкретно компилятор биндится, это отдельный заход).
- **`cxx/traaxx/CMakeLists.txt`** — `target_link_libraries` содержит закомментированную строку `# Boost::headers` (единственное упоминание Boost в CXX-сборке) — то есть сама библиотека `traaxx` уже спроектирована с местом под Boost-заголовки, но подключение сейчас выключено комментарием, и даже если раскомментировать — `find_package(Boost)` не будет вызван, потому что `PROJECT_DEPS` в корневом `CMakeLists.txt` пуст.

Итого: для сборки **любой** SIMD- или parallel-STL-реализации на C++ прямо сейчас не хватает (в порядке необходимости):
1. Раскрытия `PROJECT_DEPS` в `CMakeLists.txt` под конкретно выбранную библиотеку (не Boost — см. §3);
2. Пакета в `Dockerfile.dev` под неё же (xsimd — header-only, можно просто скопировать/apt/conan; Highway — нужен build+link; `std::experimental::simd` — не нужно ничего доустанавливать, уже есть в системном GCC);
3. Для parallel-STL-варианта — `libtbb-dev` в `Dockerfile.dev` (сейчас нет) плюс `target_link_libraries(... TBB::tbb)` или `-ltbb` в CMake;
4. Компилятора `clang` в самой live-среде отсутствует физически (см. §0) — хотя это, вероятно, специфика именно этой сессии агента, а не самого Docker-образа (в `Dockerfile.dev` `clang` прописан явно).

## Итоговый вывод

Формулировка "4 реализации: parallel STL / boost.simd / Go stdlib / Go simd" **не выдерживает встречи с фактами** ровно в двух местах из четырёх; в двух других — работоспособна с уточнением версий:

1. **"boost.simd" — нужно переименовать.** Boost.SIMD никогда не был частью Boost (проект NT2 не прошёл review, позже стал коммерческим bSIMD). Формулировку стоит заменить на конкретную живую библиотеку. С учётом того, что задача — SIMD-propagation по `uint32`-векторам `parent`/`sibling` и битовым маскам, разумные кандидаты, upstream-подтверждённые в этом исследовании:
   - **`std::experimental::simd`** — уже физически есть в системном GCC (`/usr/include/c++/15/experimental/simd`), не требует ничего доустанавливать, ближе всего по духу к "стандартной библиотеке C++", но API — TS-версии (не финальный C++26 `std::simd`, который в GCC пока не полностью реализован и требует `-std=c++26`, тогда как проект собирается под C++23).
   - **xsimd** — header-only, BSD-3, зрелая, простая интеграция (просто добавить заголовки/через conda-forge/vcpkg), но нужно явно завести в `Dockerfile.dev`+`CMakeLists.txt`.
   - **Google Highway** — самая широкая платформенная поддержка и masked/portable API, но требует полноценной сборки и линковки (не header-only), более тяжёлая интеграция.
   
   Рекомендация по факту доступности "прямо сейчас в системе без единой доп. установки" — `std::experimental::simd`, если для второй C++-реализации приемлемо TS-API; если нужен полноценный сторонний SIMD-фреймворк с лучшей документацией и порт-стабильностью — xsimd.

2. **"Go 1.27" — нужно проверить актуальность на момент реализации, а не считать несуществующей.** На дату этого исследования (2026-09-03) Go 1.27.0 уже вышла (2026-08-19), Go 1.27.1 — 2026-09-01. Локальное окружение агента отстаёт на одну версию (`go1.26.0`) — это вопрос апгрейда тулчейна, а не ожидания будущего релиза. Важнее версии — то, что **оба** Go SIMD-пакета (`simd/archsimd` в 1.26+, портируемый `simd` в 1.27+) требуют явного `GOEXPERIMENT=simd` при сборке, и их API официально помечен нестабильным — это стоит явно зафиксировать в спецификации проекта как принятый риск, а не пропустить.

3. **Parallel STL на libstdc++ требует TBB dev-пакета — это не решено.** Официальная документация GCC подтверждает жёсткую зависимость `<execution>` от Intel TBB 2018+ во всех версиях начиная с GCC 9.1, без исключений в более новых версиях (предположение из исходного вопроса про "GCC 13+ без обязательного TBB" не подтвердилось и должно быть отброшено). В `Dockerfile.dev` сейчас нет ни `libtbb-dev`, ни даже голого TBB-рантайма (в текущей live-сессии рantайм ТBB неожиданно уже стоит, но без dev-заголовков — этого недостаточно для сборки). Для C++ parallel-STL реализации нужно добавить `libtbb-dev` в `Dockerfile.dev` и `find_package(TBB)`+линковку в CMake.

4. **Реальность `Dockerfile.dev`/`CMakeLists.txt` сейчас — пустой каркас.** `PROJECT_DEPS` пуст, единственная строка про внешнюю зависимость (`# Boost::headers` в `traaxx/CMakeLists.txt`) закомментирована и всё равно указывает на неверную (недоступную) библиотеку. `clang` физически отсутствует в текущей live-сессии агента (хотя прописан в `Dockerfile.dev`) — при работе над последующими тикетами кода эту нестыковку стоит перепроверить именно в реальном devcontainer-сборе, а не полагаться на состояние этой сессии.

**Практический вывод для карты `.scratch/array-trees/map.md`**: формулировку "две C++ реализации (parallel STL / boost.simd)" стоит скорректировать на "parallel STL (требует `libtbb-dev`) / `std::experimental::simd` **или** xsimd" — окончательный выбор между `std::experimental::simd` и xsimd не сделан в рамках этого research-тикета (это архитектурное решение, не входит в мандат "только факты"); формулировку "Go simd, целевая версия Go 1.27" стоит оставить, но явно пометить, что это `GOEXPERIMENT=simd`-функциональность с нестабильным API, и что имеется в виду именно верхнеуровневый портируемый пакет `simd` (не `simd/archsimd`), доступный с Go 1.27.
