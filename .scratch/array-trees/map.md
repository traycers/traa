## Destination

Зафиксированная спецификация (не код), по которой можно независимо построить 4 реализации array-based дерева (теория Hsu, co-dfns/APL — `parent`+`sibling`, три параллельных массива `parent`/`sibling`/`data`) — две на C++ в `cxx/traaxx/` (parallel STL и SIMD-реализация) и две на Go в `go/` (стандартная библиотека и SIMD-пакет) — и корректно сравнить их между собой:

- общий набор операций и семантика (§4–§11, см. `docs/learning/array-trees/`);
- языконейтральный тестовый корпус деревьев и golden-результаты;
- единый CLI-контракт для проверки корректности и замера скорости;
- протокол бенчмарков и способ смотреть на результат сравнения в Grafana;
- документация теории и самой спецификации в `traa/docs/`;
- краткое описание задумки в `README.md`.

Реализация 4 деревьев, дашбордов и самого `README.md`/`docs/` — отдельная работа **после** этой карты, по зафиксированной здесь спецификации. Карта тикетов на «написать код» не заводит.

## Notes

- Источник теории: `docs/learning/array-trees/` (конспект по Aaron W. Hsu, co-dfns/APL — своя копия в этом репозитории, без внешних зависимостей) — деревья на базе массивов, `parent`+`sibling`, propagation, DFS/BFS, LCA, мутации, инварианты §13.
- traa использует единую раскладку из трёх параллельных массивов `parent`/`sibling`/`data` (SoA), без AoS-узла; payload — **шаблонный generic-параметр `T`** (однородный на дерево), а не закрытый доменный список типов. См. `[[01-representation-model]]`.
- Хранилище benchmark-результатов — своё: Prometheus/Pushgateway рассчитаны на pull-модель с живыми таргетами, а не на разовые прогоны бенчмарков. Grafana подключается к своему хранилищу отдельным data source. См. `[[06-benchmark-storage]]`.
- Структура `docs/learning/` (теория, справочное чтение) зафиксирована — многофайловый конспект без внешних зависимостей от других проектов, `§`-нумерация оригинала сохранена как якоря внутри файлов, см. `[[13-docs-structure]]`. Оргструктура **собственной** спецификации traa под `docs/spec/` зафиксирована, см. `[[15-own-spec-docs-structure]]`.
- Этот репозиторий — только про array-based деревья, самодостаточен: никакие материалы (теория, примеры, обоснования решений) не должны ссылаться на другой проект как источник или зависимость.
- При работе над тикетами этой карты — использовать `/grilling` и `/domain-modeling`, если явно не указано иное.
- Тулчейн (`[[07-toolchain-reality]]`, подробности `research/07-toolchain-reality.md`): «boost.simd» в исходной задумке — мёртвый проект, живой преемник — **xsimd** (`[[14-cxx-simd-library-choice]]`); C++ parallel-STL-реализация физически требует `libtbb-dev` (сейчас не установлен, только рантайм); Go-сторона устоялась как есть (`simd`, Go 1.27, `GOEXPERIMENT=simd`, нестабильный API — принятый риск). Google Highway тоже устанавливается в `cxx/Dockerfile.dev`, но только для экспериментов — не входит в формальное сравнение 4 реализаций. Установка недостающих пакетов в `Dockerfile.dev` — работа после карты, не тикет этой карты.

## Decisions so far

- [Представление дерева](issues/01-representation-model.md) — три параллельных массива `parent`/`sibling`/`data`; производные вектора (depth/rank/size/...) не хранятся, вычисляются по вызову; payload — **шаблонный/generic** параметр `T` (`Tree<T>`/`Tree[T any]`), один и тот же тип для всех узлов одного дерева — не закрытый доменный список (исправлено после первого прохода, см. правку в самом тикете).
- [Набор операций](issues/02-operation-set.md) — весь набор из §4–§11 без урезания: все стратегии propagation, DFS+BFS, все варианты LCA, все мутации §11, валидация §13.
- [Тестовый корпус деревьев](issues/03-test-corpus.md) — фиксированный набор форм из документа: сквозной пример §2, широкое дерево с малой фиксированной глубиной, вырожденная цепочка, сбалансированное широкое, звезда, перемешанная перестановка §7.4, испорченный набор для §13.
- [Формат корпуса и golden-файлов](issues/04-corpus-golden-format.md) — JSON, один канонический генератор, golden-файлы в репозитории на пару (дерево × операция).
- [CLI-контракт сравнения](issues/05-cli-contract.md) — единый CLI (JSON вход/выход, результат + тайминг/число проходов) для всех 4 реализаций; сравнение с golden и агрегация — во внешнем языконезависимом драйвере.
- [Хранилище benchmark-результатов](issues/06-benchmark-storage.md) — своё хранилище, не Prometheus/Pushgateway (пул-модель не годится для разовых прогонов); Grafana подключается к нему отдельным data source.
- [Реальность тулчейна](issues/07-toolchain-reality.md) — Boost.SIMD подтверждён мёртвым (никогда не входил в Boost) — формулировка «boost.simd» заменяется на живого преемника (выбор — `[[14-cxx-simd-library-choice]]`); parallel STL на libstdc++ требует доустановки `libtbb-dev`; Go 1.27 уже вышла (2026-08-19) и несёт портируемый пакет `simd` под обязательным `GOEXPERIMENT=simd` с нестабильным API — принимается как есть, риск фиксируется явно.
- [Структура docs/learning/](issues/13-docs-structure.md) — многофайловый конспект теории (`docs/learning/array-trees/` + `docs/learning/hsu-dissertation/`), полностью самодостаточный: без имён, ссылок и упоминаний какого-либо внешнего проекта, включая сквозной пример (нейтральные имена узлов). Структура собственной спецификации traa вынесена в отдельный тикет.
- [Схема JSON корпуса и golden-файлов](issues/08-json-schema.md) — `corpus/<shape>.json` (структурные вектора + `payload_type` самоописание `T`), `cases/<shape>/<case_id>.json` (один файл на именованный вызов операции с аргументами — раскладка исправлена при работе над `[[09-cli-schema-details]]`), `golden/<shape>/<case_id>.json` (`{"result": ...}`, форма зависит от категории операции); snake_case везде; мутации всегда полный снимок, не delta; propagation-стратегии — отдельные `op`, поэтому расхождение single-pass/iterative на `shuffled-permutation` — просто два разных case/golden, не спецкейс. Терминология — в `CONTEXT.md`.
- [CLI-схема: детали](issues/09-cli-schema-details.md) — вызов `runner --tree <path> --case <path>` (флаги, не stdin; `--case` — путь к файлу одного кейса) или `--manifest <path>` (батч-режим); успех — `{"result", "timing_ns"[], "iterations", "peak_rss_delta_bytes"}` на stdout, `exit 0` (включая `valid: false` от `validate_invariants` — это не ошибка); ошибка — `{"error", "message"}` на stderr, `exit 1`, один общий код. Правка (`[[10-benchmark-protocol]]`) сделала `timing_ns` массивом и добавила `--warmup`/`--repeat`/`--manifest`/`peak_rss_delta_bytes`.
- [Протокол бенчмарков](issues/10-benchmark-protocol.md) — только фиксированные формы корпуса + две новые серии масштабирования (`wide-shallow` по `n`, `degenerate-chain` по `d`, обе `∈{10³..10⁶}`, расширение `[[03-test-corpus]]`); повтор — внутри процесса (`--warmup 3`/`--repeat 20` default, CLI сам фильтрует холодные); новый batch-режим `--manifest` для бенчмарков (не для корректности); память — только в одиночном режиме, дельта peak RSS; протокольное правило — `iterations` обязательно рядом с `timing_ns` propagation-операций везде вниз по цепочке (хранилище, дашборды).
- [Grafana datasource](issues/11-grafana-datasource.md) — Postgres (нативный data source в Grafana, без плагинов), одна таблица `benchmark_samples` (строка на сэмпл, не массив); дашборд — два скейлинг-графика (по `nodes_count` и по `depth`) + парная панель `iterations` для propagation + та же пара для памяти (`peak_rss_delta_bytes`) + одна общая фильтруемая таблица для остальных комбинаций; отдельной метрики ЦП нет — её роль играют панели по `timing_ns`.
- [Выбор C++ SIMD-библиотеки](issues/14-cxx-simd-library-choice.md) — **xsimd**: header-only, простой API (типы-значения, перегруженные операторы), полноценно поддерживает gather/select, нужные для pointer doubling/batch LCA. Google Highway устанавливается в `Dockerfile.dev` тоже, но только для экспериментов — формальное сравнение остаётся про 4 реализации, не 5.
- [Layout](issues/12-layout.md) — C++: `cxx/traaxx` (std) и `cxx/traaxx_simd` (xsimd), два таргета; один `cxx/traapp` линкует обе, выбор через `--impl {std,simd}`; тесты — два отдельных таргета (`t_traaxx`/`t_traaxx_simd`), без общей параметризации. Go — симметрично: один модуль, пакеты `std`/`simd`, один `cmd/traago` с тем же `--impl`. Правка `[[09-cli-schema-details]]` — добавлен обязательный флаг `--impl {std,simd}` (один бинарник на язык вместо одного на реализацию).
- [Структура собственной спецификации traa](issues/15-own-spec-docs-structure.md) — `docs/spec/`, отдельный файл на тему (`operation-set.md`, `corpus-and-golden-format.md`, `cli-contract.md`, `benchmark-protocol.md`), без числовых префиксов (нет единого порядка чтения между темами, в отличие от `docs/learning/`); `index.md` с оглавлением и сквозной терминологией по образцу `docs/learning/array-trees/index.md`; пишется связной прозой как самостоятельная спецификация, `.scratch/array-trees/` — только история происхождения решений, не источник содержания.
- [Содержание README.md](issues/16-readme-content.md) — краткий пересказ Destination + карта директорий (`cxx/`, `go/`, `docs/learning/`, `docs/spec/`, `.scratch/`); без инструкций по сборке/запуску (появятся вместе с реализациями); на русском, техническая терминология без перевода.
- [Стратегия проверки корректности](issues/17-correctness-testing-strategy.md) — фиксированного корпуса (`[[03-test-corpus]]`) с golden-сравнением достаточно, property-based тесты на инвариантах §13 не нужны: каждая форма корпуса уже спроектирована под свой класс нарушений, случайная генерация добавила бы шум ради малой дополнительной степени покрытия.
