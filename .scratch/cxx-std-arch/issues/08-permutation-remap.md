## Question

`docs/learning/array-trees/06-permutations.md` §7.1–§7.3 — общий механизм: gather/scatter, две таблицы `new2old`/`old2new` (взаимно обратные), и главное правило — индексные векторы (`parent`/`sibling`) при перестановке не просто переносятся, а **переводятся** (`newParent[k] = old2new[oldParent[new2old[k]]]`), в отличие от обычных векторов данных (`data[i]`), которые просто переносятся gather'ом. Этот механизм нужен как минимум трижды: DFS-переупорядочивание ([[09-dfs-reorder]]), BFS-переупорядочивание ([[10-bfs-reorder]]), компактификация после удаления поддерева ([[12-mutations]] §11.5).

Нужно решить архитектуру переиспользуемого примитива: одна функция/набор функций `apply_permutation`/`remap_index_vector`, шаблонная по типу элемента (индексные векторы `IndexT` с переводом через `old2new`, векторы данных `T` — просто gather без перевода) и по тому, строит ли она `old2new` из `new2old` сама (`inverse()`, §7.2) или принимает обе таблицы готовыми. Как это согласуется с инкапсуляцией `Tree` ([[02-tree-encapsulation]]) — примитив работает на сырых `std::vector<IndexT>`/`std::vector<T>` и вызывается изнутри методов/функций, которым он нужен, или у `Tree` появляется собственный метод `remap`, которым пользуются DFS/BFS/удаление поддерева?

## Answer

Две разные свободные функции на сырых `std::vector`, без привязки к `Tree`: `gather<T>(std::vector<T> const&, std::vector<IndexT> const& new2old) -> std::vector<T>` (простой перенос, для `data`) и `remap_index_vector(std::vector<IndexT> const& vec, std::vector<IndexT> const& new2old, std::vector<IndexT> const& old2new) -> std::vector<IndexT>` (перенос + перевод значений, для `parent`/`sibling`) — не одна шаблонная функция с параметром «переводить/нет»: каждый вызывающий код статически знает, какой вектор переставляет, параметр-политика был бы мёртвым булем.

`old2new` строится отдельной функцией `inverse(new2old) -> std::vector<IndexT>` один раз за вызов операции переупорядочения и передаётся готовой в обе функции переноса (а не пересчитывается заново внутри `remap_index_vector` на каждый вызов) — так каждая перестановка (DFS/BFS-reorder, компактификация после удаления поддерева) применяет `parent`/`sibling`/`data` через одну общую `old2new`, без лишних O(n) проходов.

Примитив никак не привязан к `Tree<T,IndexT>` — ни отдельного метода `Tree::remap`, ни зависимости от инкапсуляции (02) у него нет. Причина: потребители примитива распадаются на два лагеря по 02 — мутирующий метод (компактификация при удалении поддерева, §11.5 шаг 5) и read-only операции переупорядочения (DFS/BFS-reorder). Общий `Tree::remap()` не покрыл бы read-only лагерь без превращения тех функций в друзей `Tree`; чисто-векторный примитив работает одинаково в обоих лагерях.

**Конвенция для DFS/BFS-reorder (распространяется на [[09-dfs-reorder]] и [[10-bfs-reorder]] одинаково), по аналогии со `std::list::sort()`/`std::sort`:** одно и то же базовое имя операции в двух формах —
- свободная функция `dfs_reorder(const Tree<T,IndexT>&) -> Tree<T,IndexT>` / `bfs_reorder(...)` — read-only по 02, строит перестановку через `const`-аксессоры, собирает **новый** `Tree` через `gather`/`remap_index_vector`;
- метод `Tree<T,IndexT>::dfs_reorder()` / `::bfs_reorder()` — мутирует `*this`: та же перестановка, но `gather`/`remap_index_vector` применяются прямо к приватным `parent`/`sibling`/`data` и результат переприсваивается на месте.

Обе формы делят вычисление перестановки (`new2old`), различается только куда применяется результат.
