## Question

`docs/learning/array-trees/10-mutations.md` §11.2–§11.7, пять методов `Tree<T,IndexT>` (зафиксировано методами в [[02-tree-encapsulation]]): `append` (O(1), инвариант сохраняется даром), `deleteLeaf` (O(1), зашивание цепочки братьев через `nsibling`), `deleteSubtree`+компактификация (O(n): маска вниз от `x` через [[05-mask-propagation-strategies]] §5.1, зашивание цепочки, затем permutation/remap [[08-permutation-remap]]), `splice` (изъятие узла с подъёмом детей к деду, инвариант порядка ломается), `move` (перемещение узла/поддерева, O(1) в структуре + требует cycle-check — маска вниз от `x` **или** DFS-тест `pos[x] <= pos[q] < pos[x]+size[x]`, §11.7 шаг 1 — оба варианта явно допускает теория).

Нужно решить архитектуру этой категории: единая ли сигнатура по всем пяти (`void`, мутируют `*this`, зафиксировано в [[02-tree-encapsulation]]) или у некоторых есть возвращаемое значение (например `append` может возвращать id нового узла); какой механизм cycle-check выбирает `move` (маска — простая зависимость только от [[05-mask-propagation-strategies]], DFS-тест — зависимость от отдельной DFS-операции ради одной проверки, которую эта карта не включает как обязательную операцию в объёме мутаций); нужны ли `nsibling`/`lastchild` как параметры (переданные вызывающим кодом, посчитанные заранее через [[07-derived-vectors]]) или каждый метод сам вызывает нужные производные векторы внутри; как метод `deleteSubtree` физически заменяет содержимое приватных полей после компактификации (через тот же permutation-примитив, что и DFS/BFS, но без изменения количества измерений — просто на уменьшившемся `n`).

Пока не решено, какой механизм cycle-check выбирает `move` — умолчание на входе в тикет: **маска вниз от `x`** ([[05-mask-propagation-strategies]]), как более простой путь без внешней зависимости от DFS. Если по ходу тикета выбор склонится к DFS-тесту (`pos[x] <= pos[q] < pos[x]+size[x]`, §10.7), тикет обязан на выходе добавить `09` в свою строку `Blocked by` и оформить это отдельным решением, а не тихой сменой пути — до тех пор эта карта не блокирует `12` на `09`.

## Answer

**Без инкрементальных кешей `nsibling`/`lastchild`.** `Tree<T,IndexT>` не получает никакого приватного состояния сверх уже решённых в [[02-tree-encapsulation]] `parent`/`sibling`/`data`. Каждая мутация, которой нужны `nsibling(x)`/`lastchild(p)` (`append`, `deleteLeaf`, `splice`, `move`), вызывает соответствующие функции из [[07-derived-vectors]] заново, тем же способом, что `depth`/`rank` — полный `O(n)`-проход по `parent`/`sibling`.

**Явное расхождение с первоисточником, зафиксированное сознательно:** `docs/learning/array-trees/10-mutations.md` §11.8 заявляет `append` и `deleteLeaf` как `O(1)`. При таком устройстве обе становятся `O(n)` — без кеша узнать `lastchild[p]`/`nsibling[x]` для одного конкретного узла дешевле полного прохода нельзя (у `parent`/`sibling` нет индекса «дети данного узла»). Причина выбора — не желание соответствовать заявленной в теории сложности, а простота: `Tree` остаётся минимальным, без риска рассинхронизации кеша с реальным состоянием (в частности — краевой случай «удаляем последнего ребёнка» в `deleteLeaf`, §11.4, который первоисточник вообще не проговаривает для инкрементального `lastchild`, что и стало одним из аргументов против кеша).

**Возвращаемые значения:**
- `append(p) -> IndexT` — id нового узла (не `void`): вызывающий код почти всегда сразу ссылается на только что созданный узел.
- `deleteLeaf(x) -> void`, `splice(x) -> void` — предусловия («`x` — лист» / «`x` — не корень») вызывающий код может дёшево (`O(1)`) проверить сам через уже имеющийся `const`-доступ; нарушение — контрактное предусловие, `assert` в debug-сборке, без проверки в релизе (не валидируем то, что не должно происходить).
- `deleteSubtree(x) -> std::expected<void, ConvergenceError>` — строит маску вниз от `{x}` тем же `propagate_down_iterative` ([[05-mask-propagation-strategies]]), что и `move`, поэтому наследует тот же риск несходимости на уже испорченном дереве (например из повреждённого JSON, до `validate_invariants`); дальше — `alive = not mask`, `old2new`/`new2old` (эксклюзивная префиксная сумма `alive`), применение `gather`/`remap_index_vector` из [[08-permutation-remap]] на приватных `parent`/`sibling`/`data` — результат заменяет их на месте, векторы уменьшаются на размер удалённого поддерева.
- `move(x, q) -> std::expected<void, MoveError>`, `MoveError = { enum class Kind { would_create_cycle, tree_corrupted } kind; IndexT iterations; }` (`iterations` осмыслен только при `tree_corrupted`, ретранслирован из `ConvergenceError` внутреннего вызова пропагации) — два независимых повода не выполнить структурную правку: семантический отказ («`q` лежит в поддереве `x`», обычный ожидаемый исход) и патология (несходимость пропагации). Тихий no-op недопустим — вызывающий код обязан узнать, что перемещение не произошло.

**Cycle-check в `move` — маска, окончательно (не временный дефолт из черновика тикета):** конкретно итеративная стратегия (§5.1, [[05-mask-propagation-strategies]]) — единственная из трёх, не полагающаяся на инвариант порядка `parent[i]<=i` или предпостроенную `AncestorTable`. Это критично: `move` может быть вызван на дереве, уже прошедшем через предыдущие `splice`/`move`, топологический порядок в котором уже сломан (§11.6/§11.7 предупреждают об этом явно) — DFS-тест (`pos`/`size` из §10.7) на таком дереве не гарантированно корректен без свежего `dfs_reorder`, что дороже и менее уместно для одной проверки, чем маска.
